# Tech Selection Strategy: Why Vitest?

**Date:** 2026-02-12
**Target:** ドワンゴ (ZEN Study) 面接対策

## 1. 結論 (The Pitch)

面接官に「なぜ Jest ではなく Vitest なのですか？」と聞かれた時のキラーフレーズ：

> 「**開発体験(DX)と速度を最優先したからです。**
> ただし、Jest との API 互換性が高いため、チームの標準が Jest であれば即座に適応可能です。」

---

## 2. 技術選定の背景 (Context)

Webフロントエンドのテスト環境は長らく **Jest** がデファクトスタンダードでしたが、近年はビルドツール **Vite** の台頭により **Vitest** が急成長しています。

### 比較表 (Comparison)

| 特徴 | Jest (Traditional) | Vitest (Modern) |
| :--- | :--- | :--- |
| **アーキテクチャ** | 独自の実行環境 (CommonJSベース) | Viteネイティブ (ESMベース) |
| **設定 (Config)** | 複雑 (Babel/Transformerが必要) | **ほぼゼロ (Vite設定を流用)** |
| **速度 (Speed)** | プロジェクト規模に伴い遅くなる | **非常に高速 (HMRが効く)** |
| **監視モード** | ファイル変更検知が重い場合がある | 爆速で再実行される |
| **互換性** | **業界標準 (多くの知見・プラグイン)** | Jest互換APIを持つが、完全ではない |

### 今回 Vitest を選んだ理由

1. **設定の簡素化 (Zero Config):**
    - Next.js (TypeScript) で Jest を動かすには、`ts-jest` や `babel-jest` などのトランスパイラ設定が必要で、環境構築だけで数時間を要することがあります。
    - Vitest は「インストールして即実行」が可能であり、**「テストを書くこと自体」に時間を割くため** に採用しました。

2. **高速なフィードバックループ:**
    - TDD (テスト駆動開発) において、テスト実行の待ち時間はストレスです。
    - Vitest の高速な Watch モードは、思考を止めずにコーディングを続けるのに最適でした。

3. **モダンプラクティスへの適応:**
    - 「現状を尊重した上で、とらわれずに目の前の問題と戦う」(ドワンゴの求める人物像)
    - 既存の Jest の辛み（遅さ、設定の複雑さ）を解消する新しいツールを積極的に試す姿勢を示せます。

---

## 3. ドワンゴの環境への適応 (Adaptability)

ドワンゴ（特に歴史あるプロダクト）では、おそらく **Jest** が使われています。
そこに対しても以下のフォローを入れてください。

> 「御社のプロダクトで Jest が採用されている場合も全く問題ありません。
> Vitest で学んだ `describe`, `it`, `expect` といった構文や、`Testing Library` の使い方は **100% Jest でも通用する知識** です。
> ツールが変わっても、テストの本質（何を保証すべきか）は変わりません。」

---

## 4. 総括

**「"楽をするため" ではなく、"本質的な作業（ロジックの検証）に集中するため" に、最新の Vitest を選びました。」**
このスタンスで回答すれば、技術選定の説得力は十分です。
